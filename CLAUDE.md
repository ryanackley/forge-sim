# CLAUDE.md — forge-sim

> Short brief for LLM agents working in this repo. Points at `docs/` for specifics rather than duplicating them; those files are the source of truth.

## Core principle

> **If it works in forge-sim, it should work in Forge. If it wouldn't work in Forge, it shouldn't work in forge-sim.**

Behavioral parity is the goal. Silently succeeding where Forge would fail is a bug. Throwing where Forge would succeed is also a bug. Before adding a feature or relaxing a check, ask: *what does the real platform do here?*

## What this is

A simulated Atlassian Forge runtime. An agent (or human) deploys a Forge app into the sim, invokes resolvers, interacts with UIKit components, queries real MySQL, manipulates Custom Entities, fires triggers, all without deploying to Atlassian.

Apps run **unmodified and bundled**, the way `forge deploy` runs them: esbuild inlines each app's dependencies (`src/bundler.ts`), and the real `@forge/*` packages inside the bundle talk to the simulator through the same three globals the Forge runtime injects.

## Architecture (10-second view)

```
┌─────────────────────────────────────────────────────────────────┐
│                       ForgeSimulator                            │
│           (orchestrator — exposed at sim.*)                     │
├──────────┬──────────┬──────────┬──────────┬─────────┬──────────┤
│ kvs      │ queue    │ resolver │ sql      │ entities│ secrets  │
│ product  │ ui       │ functions│ triggers │ remotes │ realtime │
│ llm      │ webTrigs │ proxies  │ mocks    │ events  │ ...      │
└──────────┴──────────┴──────────┴──────────┴─────────┴──────────┘
         ▲                ▲                       ▲
         │                │                       │
  resolver +        Bridge (UIKit)      __forge_fetch__ / __forge_runtime__
  frontend shims     (callBridge)       (every REAL backend @forge/* package)
   (loader hooks)
```

Three integration paths into the sim, depending on which surface the app uses:

1. **The bundler** — `sim.deploy()` and headless `sim.ui.render()` run esbuild over the app first (`src/bundler.ts`), the way `forge deploy` does: backend dependencies inlined, frontend runtime pinned to absolute paths behind an interop facade. No bare specifier is resolved at runtime. `@forge/resolver`, the one package with no seam, is routed to `src/shims/forge-resolver.ts` *inside* the bundle; Node's loader hooks (`src/loader/`) do the same only for manual-packaged apps forge-sim does not bundle. Every BACKEND package left the shim list in the bare-seam migration (path 2); every FRONTEND package — `@forge/bridge`, `@forge/react`, the three `*-bridge` product packages — left it in the frontend seam migration (path 3).
2. **`global.__forge_fetch__` + `global.__forge_runtime__`** — the two backend seams real Forge injects. Apps run the REAL `@forge/api`, `@forge/kvs`, `@forge/sql`, `@forge/events`, `@forge/object-store`, `@forge/llm` and `@forge/realtime` (all in `PASSTHROUGH_OK`, no alias); `src/runtime/seam-fetch.ts` dispatches the 9 descriptor types to `sim.*` and `src/runtime/forge-runtime.ts` serves per-invocation identity. Running the real packages means the contract can't drift, their client-side validation applies, and BUNDLED backends work — there's no import left to alias, but the seams are still called.
3. **`window.__bridge`** — the one seam real Forge gives a frontend. Apps run the **real** `@forge/bridge` (no alias, no app-facing shim); `src/bridge/protocol/` dispatches its ~34 commands to a `BridgeHost`: headless (`src/bridge/hosts/headless.ts`, calls `sim.*`) or browser (`src/bridge/hosts/browser/`, bundled to `dist/bridge.js`, served at `/__forge/bridge.js` ahead of app code on every dev page, speaks WebSocket RPC). `@forge/react`'s `reconcile` arrives the same way; the renderer turns ForgeDoc into Atlaskit.

## Conventions to follow

- **No silent stubs.** If a Forge API returns data in production, our shim returns shaped data, not undefined. If we don't implement it, throw a clear "not yet implemented" error so the parity violation is visible.
- **Real package first; a seam, not a shim.** Every `@forge/*` package except `@forge/resolver` runs as Atlassian ships it, against a seam the sim installs (`__forge_fetch__`/`__forge_runtime__` for the backend, `globalThis.__bridge` for the frontend). Don't add a shim for a package that has a seam; add the missing seam answer. Apps are **bundled** before they run — `sim.deploy()` and headless `sim.ui.render()` run esbuild with every dependency inlined (`src/bundler.ts`), exactly as `forge deploy` does — so there is no module resolution at runtime and nothing for a loader to intercept. The only sim-side touches on real packages happen at bundle time and are named in `src/bundler.ts`: `@forge/resolver` routed to the shim inside the bundle, and one appended line in `@forge/api`'s i18n module. Keep that list that short.
- **Test fixtures live in `src/__tests__/fixtures/<app-name>/`.** Each fixture is a tiny self-contained Forge app (`manifest.yml` + handler files). Real-world end-to-end apps live under `~/Projects/{retro-board, okr-tracker, my-issues, ...}` and have their own e2e test files.
- **Manifest changes go through `src/manifest.ts` (parser + sim-side checks) and `src/manifest-validation.ts` (upstream `@forge/manifest` validator wrapper).** Those checks are what tell the user "your manifest is missing X" before deploy fails. Keep error messages copy-pasteable (include the YAML snippet they should add).
- **Persistence is `entities.json` + `sql.dump`.** No more `kvs.json` (removed; everything goes through the entity store). State lives under `<app>/.forge-sim/state/`.
- **Stored credentials are opt-in on every channel except `forge-sim dev`, and mocks beat the real backend everywhere.** Dev connects by default (`--offline` to skip); the MCP server and the CLI daemon only on `--connect` / `FORGE_SIM_CONNECT=1`; the test library only on `sim.loadAuthFromEnv()`. One resolver decides it (`src/auth/connect-policy.ts`) — don't add a channel that calls `loadAuthFromEnv()` around it. A mock answers for products, remotes, provider remotes and `stargate` whether registered before or after the connect (`installPrimaryHandler` in `src/product-api.ts`), whatever status it returns: a fallback to a real backend decides on `noMockAnswer()`, never on a 404/501 status. The daemon decides per `forge-sim deploy`: every deploy first `sim.unloadAuth()`s what an earlier one loaded (by provenance, so a refreshed token goes too) and only a connecting one reloads, after deploying. Tests that touch credentials point HOME at a temp dir before any import (`vi.hoisted`). See `docs/local-development/credentials.md`.
- **Release ritual includes the plugin manifests.** `npm version` bumps `package.json` only; the Claude Code plugin version in `.claude-plugin/plugin.json` and `.claude-plugin/marketplace.json` must be bumped to match by hand. The plugin version pins marketplace updates, so a stale version means installed users never see new skill or MCP changes.
- **Bumping a real `@forge/*` dependency is a three-step ritual.** The contract suite (#10) pins our shims to specific upstream versions, so a version bump is never just a `package.json` edit:
  1. `npm install @forge/<pkg>@<version>`.
  2. Run `npx vitest run src/__tests__/shim-contract-{surface,types}.test.ts`. Failures are real drift — fix the shim (or record a deliberate deviation in `KNOWN_MISSING` / `SIM_ONLY_EXPORTS` with a reason), don't paper over them.
  3. Update that package's entry in `VERIFIED_FORGE_VERSIONS` (`src/forge-package-versions.ts`) **in the same commit**. `forge-package-versions.test.ts` fails if the table disagrees with what's installed, so skipping this breaks CI.

  That table also drives the deploy-time advisory: apps whose own `@forge/*` **major** differs from ours get a warning at deploy. Majors only — intra-major drift is what steps 1–2 already catch, and warning on every patch bump would be noise the user can't act on. Changing a pinned major is a user-visible compatibility change; call it out in the release notes.
- **Test timeouts are 30s, set globally in `vitest.config.ts`.** These are integration tests — a deploy runs esbuild over a real app, and the SQL suites boot MySQL (`persistence.test.ts` needs ~12.5s per SQL test alone). Vitest's 5s default caused chronic flakiness: unrelated tests took turns crossing the cliff under parallel load, failing 2-3 per run with no overlap between runs. If you see a timeout, check whether the test is genuinely hanging before touching the budget; don't just re-run until green. Keep any inner `expect.poll`/`waitFor` budget well under the test timeout, or the test dies on its own timeout and you lose the diagnostic.
- **Stats blocks** in markdown use HTML-comment marker pairs (`BEGIN:STATS` and `END:STATS`, each wrapped in `<!-- ... -->`) and are rewritten by `scripts/update-stats.mjs`. Don't hand-edit numbers inside markers; re-run the script. The known generators are `STATS`, `STATS_COMPACT`, and `MCP_TOOLS`. See the script for details.
- **`npm run docs:stats` is a release chore, not a per-commit step.** Don't run it after every change that adds tests: it reruns both full test suites just to count them, pollutes feature commits with doc churn across README/ROADMAP/CLAUDE.md, and any suite flake turns into troubleshooting the stats script instead of the actual work. Stale numbers between releases are fine. Run it (and `docs:stats:check`) once as part of the release ritual.

- **Bridge commands live in one place.** Adding or changing one means `src/bridge/protocol/commands.ts` (registry) + `dispatcher.ts` (frame → typed call) + a method on `BridgeHost` implemented by **both** hosts. `bridge-protocol.test.ts` re-derives the command list from the installed `@forge/bridge`, so a bump that adds a command fails CI until it is routed. Never resolve `undefined` for a command: unknown/unsupported must reject. Don't reimplement a frame from memory — read `node_modules/@forge/bridge/out/<module>.js` and cite it; every bridge bug in #40 and the consolidation was a frame detail guessed wrong.
- **Backend seams live in one place.** `src/runtime/seam-registry.ts` records everything the real `@forge/*` backend packages ask of `global.__forge_fetch__` (9 descriptor types) and `global.__forge_runtime__` (11 fields), each with a `node_modules` file:line. `runtime-seam.test.ts` re-derives both tables from the installed packages — and checks registry field names against the `ForgeRuntime` type in `runtime.d.ts`, an independent source — so a bump that sends a new descriptor or reads a new runtime field fails CI. Same rule as the bridge: cite the source, never reconstruct a shape from memory. Note `when: 'import'` on a runtime field — those are read while the package's module body evaluates, so a per-invocation value is impossible there (it's why `runtime.kvs` is deliberately omitted and `runtime.proxy` present-but-inert, and why the runtime global must never be undefined or `import '@forge/llm'` throws).
- **The bundler spec lives in one place.** `@forge/bundler` is a devDependency purely as the *specification* of what `forge deploy` does: `bundler-spec-contract.test.ts` reads its webpack config off the installed package (`out/config/common.js`, `out/config/nativeui.js`) and asserts our esbuild options in `src/bundler.ts` (`esbuildBaseOptions`, `RESOLVE_EXTENSIONS`) mirror the semantics that matter — JSX rules, extension order, the ignore set, HTML injection shape — and that every *deliberate* difference is recorded in `KNOWN_SPEC_DEVIATIONS` with a reason. A bump that changes either side fails CI. Real bundler output for seven bundlers is checked in under `src/__tests__/fixtures/bundler-matrix/` (generated by `lab/bundler-matrix/`, never hand-edited) and deployed by `bundler-matrix-fixtures.test.ts`.
- **Never reference out-of-band findings in commit messages or documentation.** Adversarial-trial reports, review rounds, eval runs and their finding ids ("F3", "Adv-1025 F1", "review follow-up") live outside this repo and mean nothing to a reader of the history or the docs. A commit message or doc sentence states the behaviour and the invariant, not where the problem was found; a code comment that must cite something cites a file, a line or an upstream doc.
- **Deferring work? Append to `deferred-issues.md`, don't open a GitHub issue.** Multiple agents work this repo at once; filing directly causes duplicates and races. A single agent converts that file to issues in one pass later. A few sentences per item: what's wrong, why it was left, what a fix must decide.

## Forge platform quirks that bite you

These are the ones you'll forget and re-learn the hard way:

- Handler format: `file.export` — file path relative to `src/`, dot-separated export name (e.g. `index.handler` → `src/index.js` export `handler`). Under manual packaging (`app.package.bundler: manual@2026`) the path is relative to `app.package.path` instead, and ONLY that directory is searched. No `.mjs` handlers — Forge lint rejects them, and the packaging standard requires manual-packaged handlers to be CommonJS (an ESM `.js` under `"type": "module"` draws a deploy warning).
- `@forge/react`'s reconcile protocol major (`forgeReactMajorVersion` on ForgeDoc roots) is NOT the npm major — 12.x emits 11. Pinned as `VERIFIED_FORGE_REACT_DOC_MAJOR`; revisit on every `@forge/react` bump.
- Resources are **top-level** in `manifest.yml`, not nested under modules.
- `app.runtime.name` is required (`nodejs22.x` / `nodejs24.x` / `nodejs20.x`). Manifests without it are rejected, including by us.
- UIKit modules in UIKit 2 require **both** `resource:` and `render: native`. Just `function:` is the deprecated UIKit 1 shape.
- React `StrictMode` + Atlaskit silently breaks rendering. Don't.
- Atlaskit components need `setGlobalTheme({ colorMode, ... })` at boot or they render with unresolved tokens (often invisible).
- Concurrency keys are scoped to the **installation**, not the queue. The publisher sets concurrency on the event, not the subscriber. Per Forge spec, weird in practice.
- Function timeouts vary by type: resolvers 25s, triggers 55s, scheduled/consumer up to 900s. We enforce these and warn when an invocation exceeds the limit.
- `?theme=dark|light` query string is the real-Forge convention for telling the iframe which theme to render. Custom UI apps should read `window.location.search`. Auto = OS preference.
- KVS uses `@forge/kvs`. `@forge/api`'s legacy `storage` export was REMOVED by Atlassian in June 2026 and no longer exists here either — apps must use `@forge/kvs`.
- Custom Entity Store uses `@forge/kvs.entity()`: separate API from plain KVS, but same `global.__forge_fetch__({ type: 'kvs' })` bridge underneath.
- Real `@forge/bridge` is strict where our old shim was lenient: `showFlag` throws without an `id`; `router.getUrl` requires a `NavigationLocation` with `target` and runs `new URL()` on the host's answer (so hosts return absolute URLs); `requestJira` on the backend requires a `route` tagged template, never a plain string. Fixtures written against the old shim fail on the real package for these reasons, not because the sim is broken.
- `@forge/bridge` i18n has **no bridge command**: it fetches `./__LOCALES__/i18n-info.json` and `./__LOCALES__/<locale>.json` relative to the page. The dev server answers `<page>/__LOCALES__/<file>`; headless patches `fetch`. The info file's real shape is `{ config: {...} }`.
- UI Kit dev pages keep the module key in the URL path (`/module/<key>/`), so their `view.createHistory()` is in-memory; a browser-backed history would navigate the key away and every later `invoke` would lose its placement.

## When something doesn't work the way you expect

1. Check the relevant doc in `docs/` first; that's the source of truth.
2. Check `src/__tests__/` for an existing test that exercises the same surface.
3. If the parity principle is being violated, it's a bug: file or fix.
4. If you're not sure whether real Forge does X or Y, the answer is in [Atlassian's developer docs](https://developer.atlassian.com/platform/forge/); don't guess.
